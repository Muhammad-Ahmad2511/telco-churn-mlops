# Feature store (Feast)

Feast defines and versions the features of the churn model (spec 12.1) and can
serve them from an **offline** store (historical features for training) and an
**online** store (low-latency lookups for inference).

## Status and limitations

Feast is currently a **standalone, tested demonstration**. It is not yet part of
the training or serving path:

- **Working and tested:** feature definitions, offline (training-style) retrieval
  with point-in-time correctness, materialization to the online store, online
  retrieval, offline/online skew tests, and data-quality checks.
- **Not integrated yet:** `src/models/tune.py` still reads
  `data/processed/telco_clean.parquet` directly, and the API (`/predict`) takes the
  full feature set in the request instead of looking customers up in the online
  store. Routing training and serving through Feast is open work.
- **Manual step:** the feature table is built by running
  `python -m feature_store.build_features`; it is not part of `dvc.yaml` or the
  Airflow DAG.
- Feast 0.68.0 needs pandas 2.x, so using it inside the API image or the main
  training environment would need a dependency decision first.

## Layout

| Path | Purpose |
|---|---|
| `build_features.py` | Builds the Feast source table from `data/processed/telco_clean.parquet`; runs data-quality checks. Pandas only |
| `feature_repo/feature_store.yaml` | Feast configuration (project, registry, stores) |
| `feature_repo/entities.py` | Entity `customer`, join key `customerID` |
| `feature_repo/features.py` | Feature catalogue and quality thresholds (plain Python, no Feast import) |
| `feature_repo/feature_views.py` | File source, two feature views, feature service `churn_features` |
| `materialize.py` | Offline to online materialization, plus training and online retrieval helpers |
| `../tests/test_features.py`, `../tests/test_feature_store.py` | Feature-quality tests and Feast retrieval/skew tests |

## Features

| Group (feature view) | Features |
|---|---|
| `customer_account_features` | SeniorCitizen, Partner, Dependents, tenure, Contract, PaperlessBilling, PaymentMethod, MonthlyCharges, TotalCharges |
| `customer_service_features` | PhoneService, MultipleLines, InternetService, OnlineSecurity, OnlineBackup, DeviceProtection, TechSupport, StreamingTV, StreamingMovies |

- **Types:** `int64` for SeniorCitizen and tenure, `float64` for MonthlyCharges and TotalCharges, strings for the rest (see `features.py`).
- **Source:** `data/processed/telco_clean.parquet`, a DVC-tracked pipeline output.
- **Transformation logic:** none. Values are copied unchanged from the processed data, so the offline and online stores hold identical values (checked by the skew test). Encoding is done separately by the project's scikit-learn preprocessing (`src/features/preprocessing.py`).
- **Entity key / timestamp:** `customerID` and `event_timestamp`. The raw data has no timestamp, so every row gets the snapshot time of the build.
- **Excluded:** `gender` (sensitive attribute), `Churn` (the label) and `customerID` as a feature (it is only the key).
- **Freshness:** rebuild the table whenever the processed data changes (manual for now). `check_feature_quality` reports a snapshot older than 30 days as stale.
- **Quality rules:** at most 1% nulls per feature, unique non-null keys, non-negative tenure and charges, SeniorCitizen in {0, 1}.
- **Owner:** data-ml-engineering (Student 1 in the specification).

## Two Python environments

Feast 0.68.0 requires pandas 2.x, while the main project environment uses pandas 3.
Feast therefore lives in its own environment, `.venv-feast`, created from
`requirements-feast.txt` (`uv venv --python 3.12 .venv-feast`, then
`uv pip install --python .venv-feast\Scripts\python.exe -r requirements-feast.txt`).
The two environments share only a Parquet file, which any pandas version can read.

| Step | Environment | Command (repository root) |
|---|---|---|
| Build the source table | main `.venv` | `python -m feature_store.build_features` |
| Register definitions | `.venv-feast` | `cd feature_store\feature_repo` then `..\..\.venv-feast\Scripts\feast.exe apply` |
| Materialize and demo queries | `.venv-feast` | `.venv-feast\Scripts\python -m feature_store.materialize` |
| Feature tests | `.venv-feast` | `.venv-feast\Scripts\python -m pytest tests\test_features.py tests\test_feature_store.py -q` |

In the main environment and in CI, `tests/test_features.py` runs and
`tests/test_feature_store.py` is skipped because Feast is not installed there.

## Stores

- **Development (this repository):** local Parquet offline store and SQLite online store, both under `feature_repo/data/` (git-ignored, regenerated by the commands above).
- **Production choice:** Parquet on S3 (or a warehouse) for the offline store and Redis or DynamoDB for the online store, because SQLite supports a single writer and no horizontal scaling.

## Versioning

Feature definitions live in Git, source data is versioned with DVC, and the Feast
registry is regenerated from the definitions by `feast apply`. Every MLflow run
(tuning, candidate and final runs) carries these tags, alongside the existing
`git_commit` and `dvc_data_md5`:

| Tag | Meaning |
|---|---|
| `feast_version` | Feast version pinned in `requirements-feast.txt` |
| `feature_repo_commit` | Last Git commit that changed `feature_store/` (the feature-repository version) |

They are produced by `src/models/lineage.py` and copied to the registered model
version by `register.py`.
